# Workit Reliability Delta - Spec

**Branch:** `feature/workit-reliability-delta`
**Decision:** `7f7f173f-5240-411c-b2ce-742353cd975f`

## Context

The v1.0.9 reliability release fixed semantic decision receipts, per-loop method
projection, durable worker dispatch claims, and recognized branch/PR route
denial. A post-release audit and live use found a second reliability delta:

- sanctioned external actions are unusable unless an agent discovers and shows
  the raw canonical descriptor;
- deterministic branch preflight failures are reported as uncertain outcomes;
- revision, close, reference, and policy-input failures cause avoidable retries;
- review evidence and worker transitions contain correctness traps;
- persisted state does not identify the Workit version that wrote it;
- several host capability and lifecycle claims exceed what the host can prove;
- distributed guidance does not tell agents to finish an approved plan without
  asking for permission between tasks; and
- approval questions can be the first place a spec, plan, or proposal is seen,
  and question UIs carry context that belongs in the conversation.

This delta lands before the OpenCode V2 port. V2 consumes the corrected shared
contracts rather than copying the defects.

## Goals

- Make every sanctioned action discoverable and approvable with one concise,
  user-facing question while retaining exact payload binding.
- Preserve deterministic preflight errors and truthful external-action outcomes.
- Remove avoidable protocol retries without weakening concurrency checks.
- Correct evidence, worker, writer, pause, and close state transitions.
- Stamp persisted state with the Workit runtime version that created or updated
  it while continuing to read v1 records.
- Make host capability advertisements and lifecycle handling truthful.
- Keep one task bound to one repository and provide useful linked-task guidance
  for multi-repository work.
- Execute an approved spec/plan continuously, with one atomic commit per plan
  task, unless a real blocker or new product decision appears.
- Present every artifact, plan, and proposal before asking for approval, with
  scoped short questions wherever the host can enforce the display budget.

## Decisions

- Implement the full P0-P2 audit delta before OpenCode V2.
- Keep one Workit task and writer bound to one repository checkout. Do not add
  repository-set authority.
- Keep canonical action payloads and digests machine-facing. The native question
  shows a short action summary, never the raw descriptor.
- Preserve exact action authorization: a concise approval is valid only for the
  proposal generated by the trusted adapter from the resolved payload.
- Preserve optimistic concurrency. Omitted revisions use current records;
  explicit revisions remain strict and receive actionable conflict details.
- Preserve strict verified closure and conservative worker uncertainty.
- Add metadata compatibly. Existing records without runtime metadata remain
  readable and are stamped on their next mutation.
- Do not introduce a new dependency or a second workflow/state system.
- No binding question may be the first sight of what it asks to approve; the
  shown content precedes the question, and the question only references it.

## Non-goals

- Cross-repository candidates, writers, or external-action authority.
- General shell parsing or guaranteed enforcement on hosts without a blocking
  hook.
- Relaxing review independence, behavioral RED-before-GREEN, or exact action
  payload binding.
- Migrating old `.workit/` files eagerly or rewriting them outside normal
  mutations.
- Implementing the OpenCode V2 adapter in this delta.

## Required Behavior

### 1. Concise action proposals

Mutating external actions use a proposal-before-reservation flow.

- Resolution computes the normalized request, concrete target, canonical
  descriptor, and a short operation-specific summary before mutation.
- A missing writer returns `needs_input` with the exact prerequisite and performs
  no reservation or mutation.
- A missing approval returns `needs_input` with a machine-facing proposal
  containing the descriptor/digest and a user-facing receipt-shaped question:
  `Workit decision: action`, concise presented text, and concise approved text.
- The native adapter owns the pending proposal. Each proposal has an opaque ID
  bound to its session, task, workspace, operation, descriptor digest, and
  creation time. It is one-use, uses the same five-minute freshness window and
  injectable clock as native decision receipts, expires when `age > 5 minutes`,
  and cannot be replaced by a concurrent proposal with the same summary.
- `decision.record` may bind an action descriptor only when the same session
  approved that proposal's concise content. Caller-supplied descriptor text or
  proposal ID alone is not authority. Missing, stale, replayed, ambiguous, and
  restart-lost proposals fail closed without asking the user to approve a
  different payload.
- The durable action decision stores both what the user saw and the exact
  descriptor it authorizes. Existing action decisions whose `approvedContent`
  is the descriptor remain valid.
- OpenCode asks one native question. Pi uses `ctx.ui.confirm`; CLI uses its TTY
  confirmation. Cursor/Codex/MCP remain unavailable where the caller cannot
  attest approval. No host fabricates a receipt.
- Near-miss failures identify the failed element (`header`, `purpose`, option
  labels, selected answer, presented text, approved text, freshness, session, or
  pending proposal) without exposing unrelated receipt contents.

Action summaries name the effect and target: branch to create/switch, commit
message and staged paths, branch to push, PR source/target/title, changelog path,
or YouTrack issue/minutes. The canonical JSON remains in tool state, not the
question UI.

### Plan-scoped commit approvals

After the user approves a plan, the lead records one bounded authorization for
the plan's listed commits instead of asking again per task.

- The authorization is an action decision whose approved content lists the
  repository checkout, the working branch, and each planned commit message (one
  per task). The user approves that list once, through the same concise native
  question.
- While the authorization is unconsumed, `git.commit` executes without a new
  question only when the requested message is an unconsumed listed step, the
  checkout matches, and the current branch matches the authorized branch.
- Each listed commit consumes exactly one step. Replay, an unlisted message, a
  different branch or checkout, or any plan change requires a fresh exact
  approval.
- Resolution and settlement still record the exact executed payload (HEAD,
  staged bytes digest, paths) as evidence for every commit; the plan
  authorization binds intent and scope, not unknown future bytes.
- Revoking the plan or the authorization retires the remaining steps.

### 2. Truthful action outcomes

- `git.branch_setup.target_branch` is required for `action: "setup"` and means
  the working branch being created/switched. It may be omitted only for
  `reapply_stash`. The resolved policy base is reported separately as
  `resolved.base_branch` in the descriptor and concise summary.
- The proposal resolves and binds the exact remote/base commit without mutating
  local refs (for example through `git ls-remote`). Execution may fetch that
  approved commit but must create the branch from exactly that commit. A changed
  or unavailable remote/base never silently substitutes a newer commit.
- The proposal also binds the current source HEAD and dirty-tree state used by
  preflight. If either changes before execution, the action returns
  `not_started` and requires a newly resolved proposal.
- Branch setup distinguishes failures before mutation from failures after a
  mutation may have started.
- Branch setup performs all validation before creating the manifest directory or
  changing HEAD, index, stash, or manifest bytes. Its result carries a structured
  mutation phase rather than requiring callers to infer it from error text.
- Protected/disallowed branch, dirty tree with `stash=no`, missing base, missing
  manifest input, and other proven preflight failures return their original
  message with `outcome: not_started`.
- For `git.branch_setup`, only a failure after a mutating Git command may return
  `external_outcome_unknown`. Remote actions retain their existing conservative
  unknown-outcome rules.
- A not-started failure settles the reservation as `not_started`; it does not
  strand or consume authority as an uncertain action.
- Error details include the resolved operation and safe retry guidance.

### 3. Protocol ergonomics

- Agent-facing schemas and bootstrap guidance prefer omitted revisions. A real
  revision conflict returns current task/workspace revisions and says whether
  omission or an intentional retry is appropriate; explicit checks remain
  strict.
- `task.close.decisionIds` is optional and deprecated as caller input. Closure
  derives decision/evidence IDs from current evaluation and never asks the agent
  to repeat them.
- `requirements_unsatisfied` returns each blocking rule ID, reason, satisfaction
  text, and dependent action instead of hashes alone.
- `writer.acquire` and `writer.release` both accept an optional reason.
- Validation failures include the rejected field path and the expected shape;
  policy assessment errors do not require source-grepping.
- Policy projections distinguish enforced gates from context. `before` and a
  concrete `dependentAction` are emitted only where core checks them; generic
  placeholder actions are removed. `prior`, preferences, and authority refs are
  labelled as policy context and never presented as enforcement receipts.
- Receipt near misses use the diagnostics from section 1.
- A repository-escaping scope reports the offending path and instructs the lead
  to keep this task in the current repository and coordinate a separate linked
  task in the other checkout.
- A local document outside the checkout is cited as an `external` `file://` URL.
  The error for an escaping `file` ref gives that exact alternative. It never
  grants candidate or writer scope over the external file.
- Task summaries expose deterministic `createdAt`, `updatedAt`, and blockers for
  active/paused tasks so abandoned tasks are visible without computing unstable
  wall-clock ages or requiring a full inspect.

### 4. Evidence and state correctness

- A fresh-context reviewer may record supporting checks and its review from the
  same independent session. The session must still differ from the task creator
  and from any other accepted fresh-review session. Self-review rules remain
  unchanged.
- Evidence auto-binds the current candidate before worker candidate-pin
  validation. A worker pinned to that candidate succeeds; a genuinely different
  candidate still fails.
- Cancelling or stopping a worker releases workspace writer ownership only when
  that writer belongs to the same worker, in the same atomic mutation.
- `cancelling` never returns to `running`. A late child-start observation binds
  the child while preserving `cancelling`; only host-confirmed termination may
  settle it to `stopped`.
- Close, revise, resume, and replacement launch use one shared definition of
  active or uncertain worker state. Assigned, dispatching, running, and
  cancelling workers never silently disagree across operations.
- Pausing preserves `progress.summary`, `nextAction`, and blockers. The pause
  reason is stored separately and cleared on resume.

### 5. Runtime metadata

Every persisted task and workspace may carry:

```json
{
  "runtime": {
    "createdWith": "1.0.9",
    "updatedWith": "1.0.10"
  }
}
```

- New records set both fields from the running package version.
- Every successful mutation updates `updatedWith` atomically with the record.
- Import preserves `createdWith` and stamps the destination runtime as
  `updatedWith`.
- Existing v1 records may omit `runtime`; parsers accept them and the next
  mutation adds `{ "createdWith": null, "updatedWith": "<current>" }`. Workit
  never fabricates the creator version of a legacy record.
- Export/import, recovery, candidate digests, and decision/evidence digests do
  not treat runtime metadata as user evidence or authority.
- Inspect/list surfaces the metadata so a bug report can identify the writer
  version without reading raw `.workit/` files.

### 6. Host truthfulness and shared execution

- Capability names use the same vocabulary as method IDs, rule IDs, and policy
  dimensions. `unavailable`, `agent_guided`, and `enforced` remain reachable and
  tested for each selected method.
- Cursor does not pretend `subagentStop` can identify a child when the event lacks
  stable identity. It advertises the limitation and leaves uncertain workers for
  explicit reconciliation.
- MCP advertises only mutations its caller provenance can perform; unavailable
  operations remain discoverable through read-only capability/context output,
  not callable schemas that can never succeed.
- OpenCode stale-source detection resolves the actual packaged/core source marker
  and tests both source and bundled layouts.
- External-action adapters share core resolution, proposal, execution, and
  settlement helpers. Adapter code owns only native approval/observation mapping.
- CI-red and pre-merge contexts select or nudge `workit-green-run` and
  `workit-blast-radius` from distributed guidance, not repository-only text.

### 7. Continuous approved-plan execution

The invariant bootstrap and `workit-plan` skill state:

- once the user approves implementation of a spec/plan — after it has been shown
  per section 8 and approved with a scoped question bound to its file digests —
  execute all remaining approved tasks in order;
- make one atomic commit per plan task after its checks pass;
- do not ask "continue?" between tasks; and
- stop only for a new product decision, failed safety/verification gate,
  conflicting concurrent edit, or unavailable required authority.

This is execution guidance, not blanket approval for optional external actions;
Git commits, pushes, and PRs still use their existing action authority.

### 8. Present before asking

No approval question may be the first place an artifact, plan, or proposal
appears. The item is presented in the conversation, then a scoped question asks
for the decision.

- Durable spec or plan: the message shows the complete reviewable digest (every
  requirement, decision, task, commit, and acceptance criterion) plus the exact
  repository path(s); the raw text remains canonical in the file and is shown on
  request.
- Non-durable plan or agreement: the content (or its complete digest for longer
  inline material) is visible in the conversation before the question.
- Action proposals: the concise summary from section 1 is the shown item.
- The question is scoped to the shown item: one short sentence naming it.
  Context belongs in the message above, never packed into the question UI.
- Workit binding questions stay within a shared display budget (a
  single-sentence question and short approved text). Artifact bodies, canonical
  payloads, descriptors, digests, markers, and tokens never appear in the
  question UI. Exact bytes bind through `binding.contentRefs` file refs with
  digests, and existing verification already rejects changed bytes.
- `approvedContent` remains exactly what the user saw and approved: a concise
  approval statement, not the artifact.
- Where the host provides a pre-execution question boundary, OpenCode denies an
  oversize or mis-shaped Workit binding question before it is displayed, with
  show-first guidance. Where the host cannot block before display, recording
  fails closed with the same guidance and mints no receipt. Hosts never claim
  enforcement they do not have.
- After a user-requested modification, update the artifact, re-present the
  changed content, and ask a new scoped question. An approval never survives
  content changes.
- Ordinary (non-binding) questions follow the same presentation guidance; the
  mechanical budget applies only to Workit binding questions.

Playbook examples (all observed in real sessions):

- Asking to approve a spec, plan, or commit before the user has seen it is a
  show-before-ask violation: present the digest plus exact path (or the content
  itself), then ask one scoped question.
- An answer with custom text is steering, not approval: no receipt is minted.
  Record the steer, adjust, re-present, and only then ask a new scoped question
  — never re-ask the identical question to mint a receipt.
- A proposal must name the concrete effect unambiguously. When a field name or
  tool semantic invites confusion (for example a working-branch argument that
  reads like a base branch), fix the surface or the proposal wording instead of
  relying on prose explanation.
- Approved-plan execution never re-asks "continue" and does not turn routine,
  already-approved plan steps into fresh questions. Where a native receipt is
  still required for one external action, the question is scoped to that shown
  step, and a changed resolved payload requires a new proposal.

## Compatibility

- Storage remains schema version 1; new runtime and pause fields are optional to
  the new reader. Pre-delta strict runtimes reject newly stamped records through
  their existing generic fail-closed path and are not claimed to provide new
  diagnostics or forward compatibility. Delta-and-later runtimes use runtime
  metadata to provide actionable upgrade guidance when they encounter a newer
  writer version.
- Existing descriptor-in-`approvedContent` action decisions continue to work.
- Existing records and exported bundles round-trip without an eager migration.
- Public `Result<T>` and error codes remain; this delta uses the existing
  `needs_input`, `revision_conflict`, and `external_outcome_unknown` codes.
- Host behavior differs only where native capabilities differ and those
  differences are explicit.

## Acceptance Criteria

- CA-01: A first mutating action call returns a concise approval proposal and the
  writer prerequisite without mutation; one matching native approval authorizes
  only the exact resolved payload.
- CA-01a: Concurrent proposals with identical summaries cannot substitute,
  replay, overwrite, survive restart, or cross the five-minute expiry boundary
  as valid authority.
- CA-02: The approval question contains no canonical JSON, commit hash, marker,
  token, or raw payload; those remain available to trusted adapter code.
- CA-03: A branch preflight rejection returns `not_started` and the original
  reason without creating directories or changing Git/manifest state; an
  injected post-mutation uncertainty remains `unknown`.
- CA-03a: A remote base advance between proposal and execution either creates the
  branch from the approved base commit or fails `not_started`; it never uses the
  newer commit implicitly.
- CA-04: Revision and close failures name the current revision or blocking rule
  and remedy; `decisionIds` omission is accepted; task summaries expose stable
  timestamps and blockers.
- CA-05: One-repository scope and external `file://` reference guidance are
  explicit and do not widen authority.
- CA-06: An independent reviewer can record checks plus review in one session;
  the creator and duplicate reviewer sessions remain rejected.
- CA-07: Candidate auto-binding precedes worker pin validation, and mismatched
  pins still fail.
- CA-08: Cancel/writer, cancelling/running, close/revise worker handling, and
  pause/resume state pass transition tests.
- CA-09: New and mutated records expose correct runtime metadata; old records,
  import/export, and recovery remain compatible; pre-delta runtimes fail closed
  generically, while delta-and-later version-skew errors include upgrade
  guidance.
- CA-10: Capability selection, Cursor stop limitation, MCP advertisement, stale
  source detection, and external-action adapter parity are truthful in tests.
- CA-11: Every distributed host receives continuous-plan, green-run, and
  blast-radius guidance; copied skill assets remain byte-identical.
- CA-12: Focused RED/GREEN tests, full checks, deterministic acceptance, packed
  release-candidate verification, deslop, and fresh-context review pass before
  delivery.
- CA-13: A durable spec/plan approval question is asked only after the complete
  digest and exact path are visible; the question is a single scoped sentence;
  approval binds file digests and fails after any byte change.
- CA-14: An oversize or mis-shaped Workit binding question is denied before
  display where the host can, or fails at record time with show-first guidance;
  no receipt is minted, and a boundary-sized scoped question still passes.
- CA-15: A non-durable plan or agreement is visible before its approval question.
- CA-16: Bootstrap and `workit-plan` teach show-then-ask for durable and inline
  artifacts; copied host skills remain byte-identical.
- CA-17: One approved plan-scoped commit authorization lets each listed commit
  execute once without a new question; unlisted messages, branch or checkout
  mismatches, and replays still require exact approval; every executed commit
  still records its resolved payload.
